# Seki host-boundary contract

- Contract revision: 2
- Decision ABI revision: 2
- Status: frozen for the A0 alpha
- Applies to: C translation units generated by `sekic build --c`

This document states exactly what crosses the boundary between a host program
and a Seki decision kernel, and what a kernel does not do. It is deliberately
short. A consumer integrating against a generated kernel should be able to read
all of it.

`tools/check_host_boundary.mjs` verifies the mechanical claims below against
what the compiler actually emits, so this file cannot drift from the compiler
without `make check` failing.

## 1. What Seki does not do

**A kernel consumes already-authenticated identities. It never authenticates
anything itself.**

A generated kernel does not and cannot:

- verify a signature, certificate, receipt, or attestation;
- recompute a digest, or compare one against anything the caller did not pass;
- read a file, open a socket, consult a clock, or call into the host;
- allocate memory, recurse, or loop unboundedly;
- observe anything outside its one parameter value.

Whether the bytes in a `Digest[sha256, 32]` field are the digest of anything at
all is a fact established upstream. The kernel decides only whether the values
it was handed stand in the relationships its policy requires.

Authority for authentication rests entirely with the host. Seki narrows what a
decision means; it does not widen what the host has established.

## 2. Evidence and the Boolean rule

Nominal identity types are the evidence-bearing inputs. Two distinct nominals
over the same representation do not compare, so a kernel cannot be written that
accepts a pack identity where an artifact identity was required. That is
enforced when the kernel is checked, and it is a guarantee about **what the
kernel does**.

It is not a property of the C type system. In the generated header the two are
distinct typedef names over the same representation, and C will not stop a host
from putting one into a field declared as the other. Filling the record
correctly is the host's responsibility, like authenticating what goes into it.

**A `Bool` input carries no evidence.** It is the host asserting a verdict the
kernel cannot examine. A kernel whose decision turns on a `Bool` parameter has
delegated the decision back to its caller and adds nothing.

Hosts should pass the identities and quantities a policy is about, and let the
kernel state the relationships. Passing `receiptValid: Bool` moves the
authority to whoever set that field; passing the two identities and letting the
kernel compare them does not.

Seki does not currently reject a kernel that depends only on `Bool` inputs.
This rule is a contract on the host, not yet a compiler check.

## 3. What the host passes in

One value, by value, of the kernel's declared parameter record.

```c
seki_a0_<module>_decision
seki_a0_<module>_<kernel>(seki_a0_<module>_<record> seki_p_<parameter>);
```

Record fields are named `seki_f_<field>` and appear in canonical field order,
which is by field name and not the order the source declared them. Widths are
exact: `U8`/`U16`/`U32`/`U64` project to `uint8_t`/`uint16_t`/`uint32_t`/
`uint64_t`, and `Bytes[N]` and `Digest[sha256, N]` project to `uint8_t[N]`.

The host is responsible for initialising every field. A kernel reads only what
it is given, but it reads whatever it is given: an uninitialised field is an
unspecified decision, not a rejection.

## 4. What the host gets back

```c
typedef struct {
    uint32_t abi_revision;
    uint32_t disposition;   /* 1 accepted, 2 rejected */
    uint32_t rejection_tag; /* 0 when accepted */
    uint32_t premise_tag;   /* 0 when inapplicable */
    /* the accepted value, when the kernel accepts something other than Unit */
    /* a union of rejection payloads, when any case declares one */
} seki_a0_<module>_decision;
```

- `abi_revision` is `2`. It rotates whenever the layout or the meaning of a
  field changes, independently of this contract's own revision. Read it first.
- `disposition` is `1` (accepted) or `2` (rejected) for every admitted parameter
  value. The kernel never writes `0`. A decision whose `disposition` is `0`
  therefore means the host passed a value that is not admitted — see section 6.
- `rejection_tag` is the stable tag the kernel's source declares with `@ N`.
  It is authored, never derived from declaration order. Tag `0` is reserved and
  never names a case.
- `premise_tag` is, when the rejection was produced by a `require`, the
  one-based precedence position of that premise. It is `0` when the kernel
  accepted, and `0` when the rejection was produced by `reject` rather than by
  `require`. `rejection_tag` identifies the case in every rejection;
  `premise_tag` additionally identifies which `require` produced it.

The tag dictionary is per kernel. Tags need not be unique across kernels.

### Comparing decisions

Every named field has a defined value: `abi_revision`, `disposition`,
`rejection_tag`, `premise_tag`, and the members of whichever accepted value or
rejection payload is live. **Compare those.**

**Do not compare whole decisions byte for byte.** The kernel zeroes the entire
decision before writing any field, and on the toolchains we have tested, padding
and inactive union members remain zero afterwards. But C does not guarantee it.
C11 §6.2.6.1 leaves padding bytes with unspecified values when any member of a
structure is stored, and leaves the bytes of a union that belong only to other
members unspecified when one member is stored. Returning the decision by value
need not copy padding at all. So a byte comparison of two decisions identical in
meaning can report a difference on a conforming compiler.

Making whole-decision byte comparison portable would need a layout with no
implicit padding and no union. That would be a future ABI revision; it is not a
property of this one.

## 5. Rejection precedence

When several premises would fail, the one reported is determined by the
kernel's declared `rejects:` order, not by how the body happens to be written.
Rejection indices must increase along every reachable path; a kernel that
contradicts its own declared order does not compile.

## 6. Failure behaviour

A generated kernel is total over its admitted inputs. It returns a decision
for every admitted value of its parameter type and has no failure mode of its
own.

A value is not admitted if a field of variant type carries a tag that is not one
of that variant's declared cases. In this revision that is the only way to pass
a non-admitted value. For such a value the kernel returns `disposition` `0`
rather than a decision. That is deterministic and detectable, and it is the only
circumstance in which `disposition` is `0`.

Failures that can occur before that point belong to the tools, not the kernel:

- malformed source, failed checking, or a backend failure cause
  `sekic build` to write **no core and no C**, and exit nonzero;
- a malformed typed core causes `sekic inspect` to fail without output.

There is no runtime error path and no partial result. The three cases a host
may need to tell apart are therefore:

- **a kernel rejection** — `disposition` `2`;
- **unadmitted input that reaches a kernel** — `disposition` `0`;
- **tool failure** — happens before any kernel exists to call, and produces no
  artifact at all.

## 7. What is frozen here, and what is not

Frozen as of contract revision 2:

- the assertions in sections 1 and 2;
- the decision struct's first four fields, their order, types and meanings;
- the meanings of `disposition` `0`, `1` and `2`, the reservation of tag `0`,
  and zeroing the whole decision before any field is written;
- rejection precedence following the declared order;
- the parameter-passing convention and the `seki_f_` / `seki_p_` spellings.

Not frozen, and expected to move before the subset, encoding and ABI are frozen
together:

- the surface syntax;
- the canonical binary encoding;
- generated identifier prefixes beyond those named above;
- payload binders in `match`, which this revision rejects rather than provides.

A correction to what this contract **says** about anything in the first list
rotates this contract's revision. A change to the decision **layout**, or to the
**meaning** of any field, additionally rotates `abi_revision`. Rotating the ABI
revision for a wording correction would tell every consumer their decision
changed when it had not.

## Revision history

**Revision 2.** Corrects statements in revision 1 that were stronger than what
is true. No layout and no field meaning changed, so `abi_revision` remains `2`.

- Nominal distinctness was described as surviving into the generated C. It is a
  guarantee about what a kernel does; C will let a host mix the two types.
- `disposition` was described as always `1` or `2`. A non-admitted value
  returns `0`.
- Decisions identical in meaning were described as comparing equal under
  `memcmp`, including padding and inactive union members. C does not guarantee
  that; compare the defined fields instead.
- The kernel was described as total over every value of its parameter type. It
  is total over admitted values.
- `premise_tag` was described loosely as the premise that failed. It is set only
  for rejections produced by `require`.

**Revision 1.** The first frozen contract.
